# 設計の背骨

**センサ → 推定 → 制御 の順に、内側のループから外側へ。**
各歩は前の歩の上に足すだけで、後から作り直す歩を作らない。

**二十八歩（手動ホバリング）が中間ゴール**で、ここまでは Optical Flow に
一切依存しない。PMW3901 が無くても価値がある地点まで先に到達する。

# 推定はすべて相補フィルタ

座標系は **FRD**（x 前、y 右、z 下）。角度はオイラー角（小角なのでジンバルロック無視）。

## なぜ相補フィルタか

ホバリングは **±15° 以内・高度 0.3〜1.5m** の狭い動作域で、この範囲では
相補と Kalman の精度差が実用上出ない。一方コード量と説明コストは 10 倍違う。

| 却下した案 | 理由 |
|---|---|
| EKF | 位置・速度・姿勢・バイアスを一括推定できるが、破綻時に何が悪いのか追えない |
| Madgwick | 実装は短いが、クォータニオン導入でロール・ピッチが「読めば分かる値」でなくなる |
| 高度だけ KF | 下記の固定ゲイン 2 状態相補が KF の定常ゲイン版と等価。共分散更新を省く分短い |

## 姿勢（25 歩）

```
roll_acc  = atan2(ay, az)
pitch_acc = atan2(-ax, sqrt(ay² + az²))
roll  = α·(roll + gx·dt) + (1-α)·roll_acc      α ≈ 0.99 @400Hz（時定数≈0.25s、要実測）
yaw  += gz·dt                                   ジャイロ積分のみ
```

ジャイロバイアスは起動時 2 秒の平均を引く。温度ドリフトは accel 側が吸収する。

**磁気センサ(BMM150)は使わない。** ヨーの絶対値はポジションホールドに不要
（ヨーレート 0 を保てば足りる）で、室内では鉄筋・家電で狂い、
キャリブレーションという歩が余計に増える。

## 高度（30 歩）

ToF は機体固定なので、傾くと斜め距離を測る。**傾き補正が必須。**

```
h_tof = d_tof · cos(roll) · cos(pitch)
予測(400Hz): vz += az_w·dt ; h += vz·dt          az_w は accel の鉛直成分 − g
補正(ToF 新データ時): e = h_tof − h ; h += k1·e ; vz += k2·e
```

ToF が 30Hz でも 400Hz で滑らかな `h, vz` が得られ、`vz` を D 項に使える。

却下: **ToF 差分で vz を作る。** 30Hz・数 mm 量子化の差分は D 項に使えるノイズ品質でない。

## 速度（32 歩）— Optical Flow の核心

PMW3901 の出力は「前回読み出しからの累積ピクセル移動量」。m/s にするには 3 段。

```
Δθx   = Δpx · K_px            K_px ≈ 0.02 rad/px ← **この値は誤り。下記の訂正を参照**
Δθx_t = Δθx − gy·dt           ★機体が傾くと、動いていなくても地面が流れる。その分を引く
vx    = h · Δθx_t / dt        h は高度推定の値（ToF 生値ではない）
```

**★の回転成分除去を省くと発振する**（傾く→流れを検出→補正で傾く）。
32 歩の検証「その場で傾けるだけなら速度≈0」はこれを見るためのもの。

有効条件（ゲート）: `h ≥ 0.10m`（PMW3901 の最小動作距離≈8cm）かつ `SQUAL ≥ 閾値`。
無効なら `vx=vy=0` として位置積分を凍結する。

## 訂正: K_px の推定値が 1 桁違っていた (2026-09-06 追記)

> **訂正**: 上の `K_px ≈ 0.02 rad/px` は誤り。参照実装の実測値は
> **0.00222 rad/px** で、約 9 倍のずれがある。
> 詳細と他の実測定数は [[stampfly-ecosystem-reference]]。
>
> **この節は「視野角と画素数からの概算がどう外れるか」の記録として残す。**

### 何を見誤ったか

視野角[rad] ÷ 有効画素数 という概算で出したが、**その視野角の値自体を
確認していなかった**。「要実測」と添えてはいたが、桁が違う値を初期値として
置くと、実測時に「合わない」ことに気づけず別の原因を探すことになる。

**条件の書かれていない概算値は、条件が違えばそのまま嘘になる。**
他の定数も同様に見直しが要る:

| 定数 | 当初の推定 | 参照実装の実測値 |
|---|---|---|
| K_px | 0.02 rad/px | **0.00222** |
| 最小高度 | 0.10 m | 0.02 m |
| SQUAL 閾値 | 32 | 0x19 (25) |

# 制御ループは単一 400Hz、外側は間引き

```
loop():
  Timer_sync()                      // 2.5ms
  Imu_update(); Attitude_update()   // 400Hz  推定 + 角度P + 角速度PID
  if (frame % 4 == 0):              // 100Hz
      Flow_update(); Tof_update()
      Altitude_update()             //   → throttle
      Position_update()             //   → roll_sp, pitch_sp
  Safety_update()                   // 400Hz
  Mixer_update(); Motor_update()    // 400Hz
```

カスケード: `位置P → 速度PI → 角度P → 角速度PID → ミキサー`。
外側ほど遅く、外側の出力は必ず内側の目標値になる。
スティックは速度指令として入る（中立 = 0 = ポジションホールド）。

**なぜ現在の 10ms では足りないか**: 36g の機体は慣性が小さく角加速度が大きい。
100Hz だと角速度ループの位相遅れ（ワースト 10ms）が大きく、発振回避のために
ゲインを落とすと風や重心ずれに負ける。公式ファームウェアも 400Hz。

> **400Hz 化は二十四歩でやる。** PID ゲインは周期に依存するため、
> 二十七歩以降に変えるとゲインを二度詰めることになる。

却下: **FreeRTOS でタスク分割。** 共有状態の排他が要り、
「どのタスクの変数か」を追うことがチュートリアルの主題ではなくなる。

# ドライバの分割

**デバイス = `Common/driver/include/driver_*.h`、機体固有の推定・制御 = `StampFly/include/*.h`**。
後者も同じ `Xxx_init / Xxx_update / Xxx_getYyy` の作法。

```
Common/driver/include/
  driver_spi.h    (23歩) SPIバスを所有。両CSをHIGHで初期化し初期化順に依存しない
  driver_imu.h    (23-24歩) BMI270。物理単位(m/s², rad/s)で返す
  bmi270_config.h (24歩) Bosch配布の設定ブロブ8192バイト
  driver_flow.h   (改) SPIClassの所有をdriver_spi.hへ移す
  driver_tof.h    (29歩) VL53L3CX下向き1個。ST公式ライブラリのラップ
  driver_power.h  (番外) INA3221
StampFly/include/
  pid.h attitude.h altitude.h mixer.h safety.h position.h
```

判断:
- **ToF は既製ライブラリをラップ。** VL53L3CX はヒストグラム方式で ST の API 一式が必要。
  VL53L1X 用の軽量ドライバは同じレジスタ列では動かない。NimBLE/FastLED に前例あり
- **BMI270 は自前で書く。** 設定ブロブ書き込みを含めて 80 行程度。Bosch の C API は
  関数ポインタでバス抽象化されており、ここでは読みにくさが勝つ
- **前方 ToF は使わない。** 2 個は同じ I2C アドレス(0x29)で、両方使うには XSHUT で
  アドレス書き換えの儀式が要る。ポジションホールドに不要なので XSHUT LOW で黙らせる
- **推定と制御は同じファイルに置く**（attitude.h に推定と PID 両方）。分けると歩ごとに
  2 ファイルずつ増える。200 行を超えたら分ける

## BMI270 の既知の落とし穴

- 電源投入直後は I2C モード。**CS の立ち上がりで SPI モードに切り替わる**ため、
  最初にダミー読み(0x00 を 1 回)をしないとチップ ID が読めない
- SPI 読み出しはアドレス送信の後に**ダミー 1 バイト**が挟まる（PMW3901 とは違う）
- バス共有では両者の SPISettings を各トランザクションで切り替える
  （BMI270: モード0 / 最大10MHz、PMW3901: モード3 / 2MHz）

詳細は [[stampfly-spi-pinout]] のバス共有の注意も参照。

# 安全性

**モーター出力は必ず `Safety_isArmed()` を通る**（ミキサーがディスアーム時に 0 を書く）。

```
DISARMED ──(全条件成立)──▶ ARMED ──(いずれか失陥)──▶ DISARMED
  アーム条件: スロットル最小 / ほぼ水平(<10°) / IMU正常 / BLE接続中 / 両トリガ1秒
  ディスアーム: 単押しでいつでも（最優先）
```

| 失陥 | 検出 | 動作 | 根拠 |
|---|---|---|---|
| リンク断 | 最終受信から 300ms | **即カット** | 36g・1m以内では落下より飛び去りが危険 |
| 傾き過大 | \|roll\|,\|pitch\| > 60° | 即カット | 反転・衝突後に回し続けない |
| IMU 異常 | 20ms 新データ無し / 全軸0固定 | 即カット | 姿勢不明の機体は制御できない |
| ToF 無効 | 200ms | 高度ホールド→手動スロットルに降格 | 飛行は続けられる |
| Flow 無効 | ゲート不成立 200ms | 位置→高度ホールドに降格、積分凍結 | 同上 |
| 低電圧 | <3.5V が1秒（**要確認**） | LED赤+ビープ。<3.3V で 2 秒かけて絞る | 姿勢制御が効かなくなる前に降ろす |
| ループ超過 | 連続発生 | LED警告（カットしない） | 診断用。カットすると振動源を特定できない |

出力上限: 最終 duty を 0.8 でクランプ。**飽和時はスロットルを下げて姿勢トルクを優先**
（4 個とも飽和すると姿勢が保てない）。位置/速度ループの目標角は ±10°、速度 ±0.3m/s。
I 項はクランプし、ディスアーム時にリセット（離陸前のワインドアップ防止）。

却下: **リンク断で自律降下。** ToF/高度制御が正しい前提が要り、
フェイルセーフの中で最も複雑な経路が、最も信頼できない状況で走ることになる。

## 運用ルール（コードではなく手順）

- プロペラ付きの歩は必ず**テザー**（糸を機体中央に結び手で保持）から始める
- 最初の離陸はクッションの上、人は 2m 以上離れる、保護メガネ
- 飛行前に JoyStick 側の電圧も確認（リンク断の原因になる）

# 既存コードのバグ

**`Common/driver/include/driver_i2c.h` の `I2C_init()` が `Wire.begin()` を
引数なしで呼んでいる。** StampFly の I2C は SDA=G3 / SCL=G4 なので、
このままでは正しいピンが設定されない。

二十一歩では I2C を実際に使っていないため露見していないが、
**二十九歩(ToF)で必ず踏む。** JoyStick 側は従来通りでよいので、
ピンが定義されていれば使う形にする。

# フォールバック — PMW3901 が無かった場合

推奨: **二十八歩 + 三十歩（手動ホバリング + 高度ホールド）を到達点とする。**
水平ドリフトはスティックで補正する。31 歩から先だけが Flow 依存なので、
**設計を作り直す箇所はない。**

どうしても位置を止めたいなら:

- **外付けモジュールを Grove ポートに付ける** — Matek 3901-L0X
  (PMW3901 + VL53L0X、MSP over UART、約1.3g)。`driver_flow_msp.h` を書いて
  `Flow_getDelta()` の同じインタフェースで返せば `position.h` は変わらない。
  **要確認**: Grove のピン、重量増(+4%)、電源電圧
- 却下: **加速度積分での位置推定** — バイアスとノイズの二重積分で数秒で発散する
- 却下: **前方 ToF で壁との距離を保つ** — 1 軸しか止まらず壁が要る。ホールドと呼べない
